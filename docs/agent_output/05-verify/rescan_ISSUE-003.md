## 2. Reasoning

Both signatures that defined the flaw are gone from the patched source: the `BasicQuery` import and construction, and the `StringBuilder` that concatenated request parameters into a JSON filter. They are replaced, at `EmployeeSearchRepository.java:22`, by `Criteria criteria = Criteria.where("name").regex(Pattern.quote(name));`, with an optional binding at line 25, `criteria = criteria.and("department").is(department);`, and the query executed at line 32 via `mongoTemplate.find(query, Employee.class)` where `query` (line 28) wraps that `Criteria` in a `Query` object. Mechanically, this closes the injection because `Criteria.where(...).regex(...)` and `.and(...).is(...)` construct a MongoDB query *document* directly from Java objects — the caller's string is placed into a single BSON field value at the driver level and is never re-parsed as JSON syntax. `Pattern.quote(name)` additionally escapes any regex metacharacters in `name` (`.`, `*`, `$`, parentheses, etc.) so that even the regex operator itself treats the caller's text as a literal substring rather than executable pattern syntax; there is no code path left, in this method, where the caller's text is concatenated into a string that is subsequently parsed as query structure. That is the distinction from the original defect, in which `new BasicQuery(filter.toString())` at the old line 31 re-parsed a hand-built string as a full query document, letting a caller who closed a quote early inject sibling keys such as `$ne`. Caller input is now bound as a value rather than spliced into query structure, which closes the reported mechanism rather than the specific payload quoted in the issue. The signatures still matching — `Criteria`, `Pattern.quote`, `@RequestParam` — are the fix's own tokens and the unchanged HTTP source, not residue of the defect.
