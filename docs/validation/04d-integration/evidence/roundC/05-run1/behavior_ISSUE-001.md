## 2. Out-of-scope changes

- Default 401 error body (framework-owned, served on the security boundary): timestamp format changed from '+00:00' offset to 'Z' (recorded probe: '2026-10-01T03:36:59.382+00:00' -> '2026-10-01T03:43:26.675Z'). The plan's acceptance bar requires unchanged payloads.
- WWW-Authenticate response header on 401 now carries a charset parameter (recorded by 04D's probe classification; the header itself is not in the excerpt this check could read).
- Malformed-JSON 400 ProblemDetail: '"type":"about:blank"' is no longer emitted and keys are reordered alphabetically (recorded probe). This contradicts plan verification step 5 ('404/409/400 error status codes and bodies match the baseline').
- Anonymous GET /actuator/health document changed shape: new livenessState and readinessState components, a new top-level 'groups' [liveness, readiness], a new ssl.expiringChains array, and key order changed (recorded probe). New sub-paths /actuator/health/liveness and /readiness now exist.
- GET /actuator/metrics meter-name list changed (e.g. jvm.classes.loaded.count added; recorded probe).
- Request deserialization is looser: before, Boot 3.5 MVC used the app's own Jackson 2 ObjectMapper (new ObjectMapper(), FAIL_ON_UNKNOWN_PROPERTIES=true), so a POST/PUT body with an unknown JSON property returned 400. After, Jackson 3.1.5 defaults FAIL_ON_UNKNOWN_PROPERTIES=false (and Boot's auto JsonMapper also disables it), so such bodies are silently accepted. This is derived statically and was not probed by 04D.
- Request deserialization is stricter for trailing content: Jackson 3 defaults FAIL_ON_TRAILING_TOKENS=true (Jackson 2 default false), so a body with trailing tokens after the JSON value, previously accepted, now fails with 400. This is derived statically and was not probed.
- H2 web console (/h2-console) is no longer served: application.yml still sets spring.h2.console.enabled: true, but in Boot 4.1.1 H2ConsoleAutoConfiguration lives in the separate spring-boot-h2console module, which is not in the migrated dependency tree (no H2Console class on the runtime classpath). Boot 3.5.0's spring-boot-autoconfigure carried it. The plan says application.yml behaviour stays unchanged, and 04D's I11 review ('no property needed renaming') did not flag the now-inert property. This is derived statically; the console was not probed on either side.

## 3. Reasoning

Fix Type VERSION_MIGRATION, compared against the fix plan's migration request and Planned changes table (pom.xml, Dockerfile, JacksonConfig, SecurityConfig, DatabaseHealthIndicator, EmployeeControllerTest, application.yml). The plan's stated bar is 'without changing how its API behaves': unchanged endpoints, status codes, payloads, authentication boundary, and 404/409/400 bodies matching the baseline. Note that the briefing's 'Planned changes' list reproduces the 6 files in the diff rather than the plan's table, so the plan itself was used as the yardstick. Materialization: the collector's worktree failed to apply the diff (CRLF diff content vs the LF-normalized clean checkout), so its signature diff ('Removed: public objectMapper()', 'Removed: public health()') is an artifact of an empty patched side and was disregarded. A supplementary LF-normalized materialization in a separate throwaway worktree supplied the patched source. Every file change traces to the plan or to the reference pack the migration request invokes, so the diff itself is in scope (with two minor plan-table deviations noted under in-scope). The runtime evidence does not stay in scope. 04D's own recorded probes (runtime/baseline.json vs final.json) show framework-owned bodies that changed while all statuses held, and 04D left exactly this as unresolved blocking constraint C8, which is why its Migration Status is PARTIAL PASS. 04D classifies them as 'expected framework change'. That is a reclassification, not an explanation by the plan, which explicitly asked for unchanged payloads and error bodies. Under the version-migration rule they are out of scope until a human accepts them. Static analysis of the migrated classpath adds three request-side and configuration changes no probe exercised (unknown-property tolerance, trailing-token strictness, H2 console removal). Not judged here whether any of these are good or bad. The security boundary (401 without/with bad credentials, 200 with demo/demo123) held in 04D's probes. It is also unverified which Jackson mapper serves HTTP after the migration: Boot 4's @Primary @ConditionalOnMissingBean JsonMapper likely coexists with the app's ObjectMapper-typed bean, so JacksonConfig may no longer be the effective HTTP configuration. Payload equivalence is observed, but its cause was not instrumented.
