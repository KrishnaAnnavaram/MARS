## 1. Remediation approach

No CWE was named in the issue or root cause report; the closest catalog entry is CWE-1104 (Use of Unmaintained Third Party Components), whose applicable_when covers a version resolved via the parent's dependency management that is no longer maintained. That entry's anti_patterns explicitly forbid treating a platform parent/BOM generation jump as a single library bump and direct it to a version_migration routed to 04d-version-migration, so the strategy moves the platform as a whole: spring-boot-starter-parent 3.5.0 -> 4.1.1 (the exact requested target, not 'latest', per canonical_approach) together with the Java level 17 -> 21 everywhere it is declared, followed by repair of the compile, configuration and test breakages the new generation introduces. Per canonical_approach, success is confirmed on the resolved dependency tree (no org.springframework.boot artifact at 3.5.x), not only on the pom text, and the issue's acceptance bar (unchanged endpoints, status codes, payloads and authentication boundary) requires a before/after behaviour comparison on top of a green build.

**Catalog pattern (`CWE-1104`):** Use of Unmaintained Third Party Components

## 2. Alternatives considered

- Bumping spring-boot-starter-parent 3.5.0 -> 4.1.1 as a single-coordinate dependency_upgrade (04c) — rejected: the CWE-1104 catalog anti_patterns name exactly this (a platform parent/BOM crossing a major generation moves managed dependencies, APIs and the Java level together), and render-fix-plan.js refuses it.
- Overriding individual managed versions (spring-framework, spring-security, jackson) under the 3.5.0 parent — rejected: leaves the unsupported platform BOM in place and mixes generations, which the root cause report identifies as not resolving the cause.
- Suppressing the finding or recording an exception for the end-of-support line — rejected: the catalog anti_patterns forbid suppressing instead of upgrading, and the organisation standard explicitly requires Spring Boot 4.1.1 on Java 21.
- Hand-editing every breakage without a previewed deterministic transformation — rejected in favour of 04D's previewed OpenRewrite recipes plus evidence-driven build rounds, which leave an auditable before/after trail.

## 4. Risks to watch

- Jackson 2 -> 3 changes the package namespace and ObjectMapper construction; a careless port could silently change date formatting or null inclusion in every response payload.
- Spring Security 7 removes deprecated APIs and may change default matcher behaviour; the authentication boundary (/api/** authenticated, actuator health/info anonymous) must be proven unchanged, not assumed.
- Hibernate under Boot 4 may parse the JPQL/native queries in EmployeeRepository more strictly; a passing compile does not prove the queries still run.
- Testcontainers explicit 1.20.1 pins sit outside the parent BOM and may conflict with the Boot 4.1.1-managed version; EmployeeRepositoryIntegrationTest needs Docker to exercise PostgreSQL.
- The service has a separate, out-of-scope application defect noted in architecture.md (email uniqueness checked via findByEmployeeNumber); the migration must not fix or alter it — behaviour must stay identical, defects included.
- The build and runtime JDK both change (17 -> 21); CI and container images must move together or the jar will not start on a Java 17 runtime.

## 5. How the fix must be verified

1. In src/spring-boot-migration-demo run `mvn -q help:evaluate -Dexpression=project.parent.version -DforceStdout` on the patched project and expect 4.1.1.
2. Run `mvn dependency:tree` on the patched project and confirm no org.springframework.boot artifact resolves at 3.5.x (the resolved tree, not just the pom text, per CWE-1104 canonical_approach).
3. Grep the patched pom.xml and Dockerfile for the Detection Notes markers `<version>3.5.0`, `<java.version>17`, `<source>17` and `eclipse-temurin:17-jre` and expect no matches.
4. Run the full build with tests (`mvn verify`) on JDK 21, including the Testcontainers-based EmployeeRepositoryIntegrationTest with Docker available, and expect a green build; record any test that could not run and why.
5. Record a baseline runtime probe on the unmodified 3.5.0/JDK 17 build and the same probe on the migrated 4.1.1/JDK 21 build: GET /api/v1/employees returns 401 without credentials and 200 with demo/demo123; GET /actuator/health returns 200 anonymously; create/read payloads keep ISO-8601 dates and omit null fields; 404/409/400 error status codes and bodies match the baseline.
6. Confirm the drafted diff touches only files listed here (any extra file recorded as a deviation with a reason) and that the real working tree is untouched — all work happens in the 04D sandbox.
