## 1. Remediation approach

Replace both unbounded MongoRepository.findAll() calls with the catalog's CWE-770 canonical approach: a paginated Spring Data read (Pageable / Page<T>) with a server-enforced maximum page size. The scheduler and report paths both walk every record by design, so each iterates pages rather than materialising one list. This closes the root cause — an allocation whose size is controlled by collection growth rather than by the application — instead of only making today's dataset fit.

**Catalog pattern (`CWE-770`):** Allocation of Resources Without Limits or Throttling

## 2. Alternatives considered

- Raising the JVM heap — rejected: moves the failure threshold without removing it; the allocation is still proportional to collection size.
- Adding a caller-supplied page-size parameter only — rejected: the catalog's anti_patterns entry flags an uncapped page size, since a caller can still request an unbounded page.

## 3. Planned changes

| File | Planned change |
|---|---|
| [EmployeeSchedulerServiceImpl.java](../../../sheduler-service/src/main/java/com/aura/vihanga/shedulerservice/service/implementation/EmployeeSchedulerServiceImpl.java) | Replace repository.findAll() with a paged read using PageRequest.of(page, MAX_PAGE_SIZE), iterating while more pages remain; keep the method signature and return type unchanged. |
| [EmployeeReportServiceImpl.java](../../../report-service/src/main/java/com/aura/vihanga/reportservice/service/implementation/EmployeeReportServiceImpl.java) | Replace repository.findAll() with the same server-capped paged read so the XLSX export streams page by page instead of materialising the whole collection. |

## 4. Risks to watch

- Both call sites feed downstream loops that assume a full List; paging must preserve total ordering and completeness or the export/scheduler output changes.
- The scheduled job's runtime will increase slightly because it issues N queries instead of one.

## 5. How the fix must be verified

1. Compile both affected modules.
2. Confirm no remaining unbounded findAll() reaches a REST handler or scheduled job.
3. Seed a collection larger than one page and confirm the export still contains every record exactly once.
