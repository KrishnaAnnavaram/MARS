## 1. Remediation approach

Apply the catalog's CWE-306 canonical approach: require authentication through the framework's security layer — a Spring Security filter chain that denies by default — rather than ad-hoc checks inside handlers, and add method-level authorisation on the payroll paths. Because the catalog's anti_patterns entry warns against securing only the endpoint named in the issue, the filter chain is applied across all affected modules so structurally identical sibling endpoints are covered too. The log exposure (CWE-532) is closed in the same change by removing PII and salary values from logger arguments and dropping the committed TRACE directive.

**Catalog pattern (`CWE-306`):** Missing Authentication for Critical Function

## 2. Alternatives considered

- A shared secret header checked inside each controller — rejected: the catalog's anti_patterns entry flags exactly this as an ad-hoc substitute for the security framework.
- Network-level restriction only — rejected: leaves service-to-service calls and the open config server unauthenticated, and provides no principal for audit.

## 4. Risks to watch

- This is the widest change in the set: six files across four modules, and it alters the response shape of GET /api/v1/employee by moving to a DTO.
- Adding a security filter chain to modules that currently have none will break any existing unauthenticated client, including internal service-to-service calls, until they carry a credential.

## 5. How the fix must be verified

1. Compile every affected module.
2. Confirm no endpoint that returns employee or salary data is reachable without a principal.
3. Grep the changed files for logger calls carrying whole entities, phoneNo, address or salary and confirm none remain.

_The Fixer's verification report must address every step above, or explain why a step could not be run (e.g. it needs a live dependency unavailable in the isolated build sandbox)._

## 6. Open questions

- Which credential mechanism the platform standardises on for service-to-service calls was not settled by the context bundle; the plan assumes the framework's security layer without prescribing the token format.
