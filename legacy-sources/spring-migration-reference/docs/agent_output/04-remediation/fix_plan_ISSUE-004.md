## 1. Remediation approach

Apply the catalog's CWE-1104 canonical_approach directly: identify the minimum version that remediates CVE-2025-31672 from the advisory's own affected/fixed range (poi-ooxml < 5.4.0 is affected, so 5.4.0 is the minimum fixed version — not simply 'latest'), pin that version explicitly in employee-service/pom.xml exactly where the vulnerable version is pinned today, and verify via `mvn dependency:tree` that the *resolved* dependency reflects the bump rather than trusting the declared <version> text alone. This is a single-line, single-file change that closes the root cause directly (the vulnerable parsing code itself is replaced) without touching any calling code, matching the root cause report's own recommended fix.

**Catalog pattern (`CWE-1104`):** Use of Unmaintained Third Party Components

## 2. Alternatives considered

- Bumping to the newest available poi-ooxml release instead of the minimum fixed version — rejected per the catalog's anti_patterns: 'latest' can introduce unrelated breaking changes to ExcelUploadImpl's usage of the POI API that are out of scope for a security fix; 5.4.0 is the precise, advisory-verified target.
- Adding structural validation to ExcelUploadImpl.isValidExcelFile() instead of (or as well as) upgrading the library — rejected for this diff: it would not close the root cause (the vulnerable library code itself), only add a second, independent layer around it. Worth tracking as a defence-in-depth follow-up, not a substitute for the version bump.
- Suppressing the finding via a dependency-check ignore/allowlist rule instead of upgrading — rejected outright per the catalog's anti_patterns; this leaves the vulnerable code in production.

## 4. Risks to watch

- poi-ooxml 5.0.0 to 5.4.0 spans several minor releases; while this stays within the same major version (5.x), the Fixer's verification should confirm employee-service still compiles cleanly against the new version's API surface, not just that the version string changed.
- This fix only addresses employee-service's direct pin — if org.apache.poi is pulled in transitively by any other module at a vulnerable version, that is a separate, untracked instance of the same root cause (see open_questions).

## 5. How the fix must be verified

1. Compile employee-service.
2. Confirm the declared <version> for org.apache.poi:poi-ooxml in the patched pom.xml is >= 5.4.0.
3. Run `mvn dependency:tree` filtered to org.apache.poi and confirm the *resolved* version is also >= 5.4.0 — not overridden by another dependencyManagement entry.
4. Confirm no other behavior in ExcelUploadImpl changes — this is a pure dependency-version bump, not a logic change.

_The Fixer's verification report must address every step above, or explain why a step could not be run (e.g. it needs a live dependency unavailable in the isolated build sandbox)._
