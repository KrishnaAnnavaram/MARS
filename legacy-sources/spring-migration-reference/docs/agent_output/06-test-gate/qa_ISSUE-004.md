## 1. What the new test proves

This is a dependency-version fix, not a logic fix, so the usual framing ('fails pre-patch, passes post-patch') does not apply the way it does for a code-level vulnerability -- a benign upload behaves identically on poi-ooxml 5.0.0 and 5.4.0, and the CVE itself is closed by the version-range fact, not by a runtime reproduction (reproducing CVE-2025-31672's duplicate-ZIP-entry payload would require bypassing java.util.zip.ZipOutputStream's own duplicate-entry guard by hand-writing raw ZIP bytes, disproportionate for this regression test). What this test actually protects against is the real, practical risk the fix plan's own risk_notes named: poi-ooxml 5.0.0 to 5.4.0 spans several minor releases, and ExcelUploadImpl.getEmployeeDataFromExcel's use of the POI API (XSSFWorkbook construction, Sheet/Row/Cell access, cell-type branching for phoneNo) must still behave identically after the bump. It builds a workbook in memory with XSSFWorkbook, wraps it as a MockMultipartFile, feeds it through the exact production method, and asserts every field of the parsed Employee round-trips correctly -- proving the version bump did not silently break the upload feature's actual behavior.

**Mocking strategy:** No mocking needed and no live dependency of any kind -- the test builds its own in-memory .xlsx via XSSFWorkbook (the same library under test) and wraps it as a Spring MockMultipartFile (from spring-test, already a transitive dependency via spring-boot-starter-test). ExcelUploadImpl.getEmployeeDataFromExcel is a static method with no Spring context or database dependency, so it is called directly.
